## 1. 项目概览

CtrlZebra 是一个**本地优先（local-first）的 VS Code 编码 Agent 扩展**。它流式渲染模型回复，可以读取选定的工作区，以可审阅的方式提议文件修改，在获得一次性授权后执行命令，并把会话与恢复检查点保存在本地。项目没有账号体系、云同步和遥测后端。

### 1.1 技术栈

| 维度 | 选型 |
|---|---|
| 语言 / 运行时 | TypeScript 6.0.2 / Node.js 22+（CI 用 24） |
| 包管理 | pnpm 11.11.0，workspace monorepo |
| 代码质量 | Biome 2.5.3（格式化 + lint 合一） |
| 测试 | Vitest 4.1.6（node + jsdom 双 project）、`@vscode/test-electron` 集成测试 |
| 前端 | React 19 + Vite 8 + Zustand（vanilla store） |
| 模型接入 | Vercel AI SDK（`@ai-sdk/openai`、`@ai-sdk/google`、`@ai-sdk/openai-compatible`） |
| 打包 | esbuild + `@vscode/vsce`，自建 VSIX provenance 校验与 smoke 测试 |

### 1.2 模块结构

## 3. 优点

这些是本次评估中明确值得保留的做法，后续改造不应破坏它们。

**工程规范度远超一般个人项目。** 14 个阶段 98 个任务全部在 `docs/implementation-plan.md` 中逐条登记了状态、完成 PR 编号和日期；`AGENTS.md` 用依赖方向表和"事实所有权"表把架构约束和文档职责写成了可执行规则；变更控制明确要求先改规格再改代码。这套东西一旦建立起来，后续无论是人还是 Agent 接手，返工率都会显著降低。

**安全模型是认真设计过的，不是事后补的。** 审批绑定到具体的不可变操作，单次有效，任何实质变更、重试、取消或消费之后立即失效；工作区路径经过符号链接感知的规范化并强制包含性校验；命令用直接 spawn 并禁用 shell 解释，环境变量最小化，超时和输出有界，终止时清理整个进程树；API Key 只进 VS Code SecretStorage，明确禁止出现在日志、快照、持久化消息和 fixture 中；写入前先提交 Checkpoint，恢复是冲突安全的（目标被改动就整体拒绝，而不是尝试合并）。

**边界隔离执行得很干净。** `packages/core` 确实不依赖 VS Code、React、Node fs 和任何模型 SDK，全部能力通过接口注入；Provider SDK 的类型和错误被限制在 `packages/providers` 内部；`extension.ts` 只做注册和组合，没有业务逻辑。取消（cancellation）被建模为独立于失败的结果，而不是普通异常。

**CI 与供应链有基本防护。** GitHub Action 全部钉到 commit SHA 而非 tag；`pnpm install` 有 lockfile 供应链策略校验；VSIX 打包要求分支干净且 HEAD 已存在于上游，产物带 SHA-256 校验和与构建摘要。

**MCP 集成的安全克制程度是对的。** 只支持一个显式配置的本地 stdio Server，拒绝 shell 命令行、环境变量覆盖、凭据注入和工作区级配置；所有 MCP 工具无条件按 `execute` 风险处理，Server 自称只读也不降低审批要求；断连、取消、失去工作区信任都会作废活动目录和挂起操作，且从不自动重连。这套安全姿态应当完整保留。

需要区分的是，**协议版本策略是另一回事** —— 把版本钉死在 `2026-07-28` 并不是上述安全考量的一部分，它是一个独立的兼容性取舍，详见第 4 节的 P1-2。

### P0-1　没有多轮对话（功能性硬伤）

### P1-2　MCP 建成了但接不上现存生态（两道独立的筛子）

这一条与其他问题性质不同：**它是显式设计决策的结果，不是疏漏**。ADR 0001 的兼容性矩阵明确写了"Older or future protocol versions → Rejected with `protocol-incompatible`"，Consequences 里也写了"Exact-version support deliberately rejects some otherwise compatible Servers"。README 的已知限制和排障章节同样如实说明。列在这里，是因为**决策成立时所依据的生态假设与当下现实不符**。

阶段 14 交付的约 5,000 行 MCP 客户端，在接入真实服务器时要连过两道彼此独立的筛子，任何一道拦下都等于不可用：

| 筛子 | 拦截对象 | 详见 |
|---|---|---|
| 协议纪元 | 说 legacy（`2025-11-25` 及更早）协议的服务器 | P1-2a |
| 工具 Schema 关键字白名单 | 工具入参用了 `format`、`pattern` 等常见关键字的服务器 | P1-2b |

两道筛子的成因和修法都不同，需要分别评估。**第二道的修复成本明显更低、收益更直接**，即使决定不做纪元降级也应该单独处理。

#### P1-2a　协议版本钉死在 `2026-07-28`

SDK 配置把版本锁死在两处：

```5:11:packages/mcp-client/src/sdk-options.ts
export const controlledSdkClientOptions = {
  capabilities: {},
  enforceStrictCapabilities: true,
  inputRequired: { autoFulfill: false },
  supportedProtocolVersions: [mcpProtocolVersion],
  versionNegotiation: { mode: { pin: mcpProtocolVersion } },
} satisfies ClientOptions;
```

SDK 对 `pin` 模式的定义是：*"modern era at exactly the pinned revision: the connect-time `server/discover` must offer it. **No fallback — anything else fails loudly with a typed error.**"* 注意 SDK 的默认模式是 `'legacy'`，项目是主动从默认值切走的。连接建立后还有第二道校验兜底：

```411:415:packages/mcp-client/src/controlled-mcp-client.ts
      if (this.transport.protocolVersion !== mcpProtocolVersion) {
        const failure = this.setFailure("protocol-incompatible");
        await this.transport.close();
        return { kind: "failed", error: failure };
      }
```

**为什么现在成了问题**：`2026-07-28` 于 2026-07-28 正式发布，距本次评估仅九天，且是 MCP 有史以来最大的一次改版——彻底移除 `initialize`/`notifications/initialized` 握手与 `Mcp-Session-Id`，协议核心改为无状态，版本与能力改由每个请求的 `_meta` 携带，新增 `server/discover`。规范将 `2025-11-25` 及更早统称为 **legacy era**，并给了至少 12 个月的下线窗口。

结论是：**今天市面上现存的 MCP 服务器几乎全部是 legacy**，阶段 14 交付的约 5,000 行 MCP 客户端，实际能连上的只有用户自己升级过的服务器。ADR 写"rejects some otherwise compatible Servers"时的语气像是在描述少数边缘情况，但真实比例是反过来的。

规范本身是明确支持双纪元客户端的，其 versioning 文档的兼容性矩阵有这一行：*"Dual-era | Legacy | Works. stdio: the probe returns a non-modern error or times out, and the client falls back to `initialize`."*

此外，当前的失败提示过于笼统 —— `packages/mcp-client/src/errors.ts:5` 是 `"The MCP Server does not support the required protocol version."`。既然 legacy 服务器是当下最可能遇到的失败原因，提示应当直接点明纪元差异和处置办法。

#### P1-2b　工具 Schema 白名单过严，且单个工具失败会废掉整个目录

即使协议纪元问题解决了，工具 Schema 还有第二道筛子，而且**它的实际拦截率可能比第一道更高**。

约束有两层。第一层是版本钉死：`packages/mcp-client/src/mcp-tool-schema.ts:12` 定义了 `draft202012` 常量，服务器若声明 `$schema` 则必须恰好是该值（`:140-144`）。但 `$schema` 是可选的，不声明就不检查，所以这一层单独看影响有限。

第二层才是重点：`walkSchema` 遍历整个 Schema，**遇到任何不在白名单里的关键字直接抛错**：

```112:115:packages/mcp-client/src/mcp-tool-schema.ts
  for (const [key, nested] of Object.entries(record)) {
    if (!allowedKeywords.has(key)) {
      throw new McpToolSchemaError();
    }
```

白名单只有 30 个关键字（`:31-44`），覆盖 `type` / `properties` / `required` / `enum` / `const` / `$defs` / 本地 `$ref` 和各类 min-max 边界。用真实生成器会产出的 Schema 实测（本次评估临时编写探针运行，未留存在仓库中）：

```text
ACCEPT  baseline (plain object)
REJECT  format: uri              ← zod .url() / pydantic AnyUrl
REJECT  format: date-time        ← pydantic datetime
REJECT  pattern                  ← zod .regex()
REJECT  definitions              ← Draft 7 / 老一代生成器
ACCEPT  $defs + local $ref       ← pydantic v2
REJECT  $id
REJECT  $comment
REJECT  readOnly / deprecated
REJECT  nullable                 ← OpenAPI 风格
REJECT  if / then / else
ACCEPT  additionalProperties: false
ACCEPT  correct $schema
REJECT  Draft 7 $schema
ACCEPT  recursive $ref
REJECT  root-level non-object
```

`format` 与 `pattern` 杀伤力最大。TypeScript 侧的 `zod-to-json-schema`（TS MCP 服务器的主流做法）为 `.url()` / `.email()` / `.uuid()` 生成 `format`、为 `.regex()` 生成 `pattern`；Python 侧 Pydantic v2 为 `datetime` / `UUID` / `AnyUrl` 生成 `format`。**任何一个参数里含 URL、邮箱、日期或 UUID 的工具都会被拒**，而这在实际 MCP 服务器里近乎标配。

**爆炸半径是整个目录，不是单个工具。** 这比白名单本身更严重：

```146:155:packages/mcp-client/src/mcp-tool-snapshot.ts
    try {
      inputSchema = validateMcpToolSchema(record.inputSchema);
      outputSchema =
        record.outputSchema === undefined ? undefined : validateMcpToolSchema(record.outputSchema);
    } catch (error) {
      if (error instanceof McpToolSchemaError) {
        throw new McpToolSnapshotError("invalid-schema");
      }
      throw error;
    }
```

这段在遍历工具列表的循环内，第一个不合规的 Schema 直接终止整个快照构建；上层原样转成 `McpToolDiscoveryError`（`controlled-mcp-client.ts:533-538`），而快照替换只发生在成功路径。所以**服务器有 20 个工具、其中 1 个用了 `format: "uri"`，20 个全部不可用**，用户只看到一句笼统的 `"MCP Tool schema is invalid or unsupported."`，既不知道是哪个工具，也不知道是哪个关键字。

**设计意图对，失败模式错。** 禁止 `pattern` / `patternProperties` 是完全正确的 —— 服务器提供的正则会被编译进 Ajv 并用模型生成的参数执行，这是典型的 ReDoS 灾难性回溯攻击面；禁止远程 `$ref`（SSRF）和各类深度/节点/字节限额（DoS）同样站得住。问题在于把两类性质不同的关键字混同了：真正危险的（`pattern`、`patternProperties`、远程 `$ref`、超限结构）应当拒绝，而仅仅是"没建模"的（`format`、`$id`、`$comment`、`readOnly` / `writeOnly` / `deprecated`、`definitions`、`nullable`、`if` / `then` / `else`、`propertyNames`、`unevaluated*`）不该拒绝。处理办法见方案 I.6。

**附带发现：文档与实现不符。** ADR 0001 第 91 行与 `docs/architecture.md:338` 都声明"cyclic references 禁止"，但实测递归 `$ref` 被接受。原因是 `assertAcyclicReferences` 记录的边起点是包含 `$ref` 的那个 Schema 对象的路径（`mcp-tool-schema.ts:149`），对 `$defs/Node/properties/child → $defs/Node` 这类自递归，起点与目标路径不相等，目标节点在图中没有出边，环检测不到。互相引用（`$defs/A ↔ $defs/B`）仍能被捕获。

这不是安全问题 —— Ajv 本身能正确处理递归引用，`cloneJsonValue` 有祖先追踪防死循环，而且递归可用其实是好事（树形/AST 类参数得以支持）。但它意味着**文档描述的约束比实际实现更严**，按 `AGENTS.md` 的事实所有权规则属于需要通过变更控制修正的偏差：要么补齐实现，要么把文档改为实际的"直接自引用允许、互相引用禁止"。

## 5. 具体实施方案

### 方案 A　打通多轮对话（对应 P0-1）

这是唯一一个必须拆成多个任务、且需要先走变更控制的改动，因为它同时触及会话状态机、跨边界协议和持久化语义。

#### A.1 设计决策

有两条路线：

| 方案 | 做法 | 评价 |
|---|---|---|
| **（推荐）扩展 Session 为多轮** | 一个 Session 容纳多个回合，`completed → preparing` 成为合法转换 | 与现有持久化结构一致（事件流本就按会话追加，恢复时重建消息数组），改动面最小 |
| 引入 Conversation 聚合 Session | 新增一层聚合根，Session 仍是单回合 | 需要新的持久化实体、新的列表 UI 和迁移逻辑，收益不明显 |

推荐第一条。理由是持久化层和 Webview 的恢复逻辑已经按"一个会话多条消息"实现，选它属于补齐接线；选第二条则要引入一个当前没有需求支撑的新抽象，违反 `AGENTS.md` 第 4.2 节"无当前用例不新增抽象"。

#### A.2 任务拆分

**T1501（契约，docs-only + protocol）**

- `docs/architecture.md`：定义多轮 Session 的生命周期，明确一个 Session 内的回合边界、状态机在回合之间的复位规则。
- `docs/protocol.md`：`webview/submit` 增加可选 `sessionId`；新增 `webview/new-chat` 消息。
- `docs/persistence.md`：明确从事件流重建 `ModelMessage[]` 的规则（哪些事件参与重建、工具调用/结果如何配对、被裁剪的历史是否回写）。
- `packages/protocol/src/messages.ts`：

```ts
export const submitMessageSchema = z.strictObject({
  ...protocolEnvelopeSchema.shape,
  type: z.literal("webview/submit"),
  content: submittedContentSchema,
  // 省略表示开启新会话；提供则在既有会话上追加一个回合
  sessionId: sessionIdSchema.optional(),
});

export const newChatMessageSchema = z.strictObject({
  ...protocolEnvelopeSchema.shape,
  type: z.literal("webview/new-chat"),
});
```

由于 Webview 与 Extension 同包发布、版本锁步，向 `strictObject` 增加可选字段不需要提升 `protocolVersion`。但恢复旧会话时必须容忍不含 `sessionId` 的历史事件。

**T1502（core）**

状态机放开回合复位：

```ts
// packages/core/src/session-state-machine.ts
  completed: ["preparing"],   // 同一 Session 内开启下一回合
```

`cancelled` 和 `failed` 是否也允许复位需要明确决定。建议**允许**，否则一次失败就废掉整个会话，用户体验很差；但要在 `docs/architecture.md` 里写清楚失败回合的消息是否进入下一轮上下文（建议：失败回合的用户消息保留，未完成的助手消息与工具结果丢弃）。

`AgentRuntime` 接收既有历史：

```ts
// packages/core/src/agent-runtime.ts

  // ...现有字段
  readonly history?: readonly ModelMessage[];

async run(userMessage: UserMessage, signal: AbortSignal): Promise<void> {
```

注意 `pruneModelHistory` 已经保护最新的用户消息和 system 消息（`history-pruner.ts:179-182`），并且成对保留工具调用与结果，直接可用。

**T1503（extension + webview）**

`ChatRunner` 接口改为携带会话：


实现里的关键改动：

`loadModelHistory` 是本任务的核心新增函数，建议放在 `apps/extension/src/controllers/session-history.ts`。它读取 `SessionRecord` 的事件流，筛出用户消息、助手最终文本、工具调用与工具结果，按时间序重建 `ModelMessage[]`。必须保证工具调用与结果成对出现，否则 `pruneModelHistory` 会抛 `InvalidModelHistoryError` —— 对于被中断的回合，应丢弃孤立的工具调用。

Webview 侧：`chat-store` 提交时带上当前 `selectedSessionId`；Header 增加 "New chat" 按钮发送 `webview/new-chat`；恢复历史会话后继续提问应当追加到该会话而不是新建。

#### A.3 测试要求

| 层 | 用例 |
|---|---|
| core 单测 | `completed → preparing` 合法、其他非法转换仍拒绝；带 history 的 run 把历史传给网关；历史超预算时被裁剪且最新用户消息保留；取消发生在第二回合时状态正确 |
| extension 单测 | `loadModelHistory` 正确配对工具调用/结果；孤立工具调用被丢弃；空会话返回空数组；损坏事件流不抛未捕获异常 |
| extension 单测 | `ChatRunner` 传 `sessionId` 时不新建会话、不重复 `create()` |
| webview 单测 | 提交携带 `selectedSessionId`；New chat 后 store 清空且下次提交不带 id |
| 集成测试 | 连续两轮对话，第二轮的模型请求包含第一轮的消息 |

#### A.4 风险

- **持久化兼容**：已有会话的事件流是按单回合写入的，`loadModelHistory` 必须能处理它们（结果通常是"只有一个回合的会话"，这是可接受的降级）。
- **审批语义**：一个 Session 内跨回合时，上一回合的审批必须已失效。现有实现是审批单次有效且绑定具体操作，理论上安全，但需要补一个跨回合的回归测试。

### 方案 B　接上重试层（对应 P0-2）

这是投入产出比最高的一项，属于 `AGENTS.md` 第 1.2 节意义上的独立维护变更 —— 不改架构、不改公共契约、不改持久化格式。

**改动点**：在 `selectModelGateway` 返回处包一层。放在 selector 内部比放在 `extension.ts` 更好，因为这样所有调用方（含未来的）都自动获得重试。

```ts
// apps/extension/src/controllers/model-gateway-selector.ts
import { type ModelGateway, RetryingModelGateway } from "@ctrl-zebra/core";

export async function selectModelGateway({
  configuration,
  requiredCapabilities,
  secrets,
  factories,
}: SelectModelGatewayOptions): Promise<ModelGateway> {
  const gateway = await createProviderGateway({
    configuration,
    requiredCapabilities,
    secrets,
    factories,
  });
  return new RetryingModelGateway(gateway);
}
```

把现有的三分支逻辑抽成 `createProviderGateway`，保持行为不变，只在最外层包装。

**注意事项**：

- `RetryingModelGateway` 的第二个参数是延迟函数，生产环境用默认值即可，测试注入假延迟。
- 不要同时打开 AI SDK 的 `maxRetries` —— 两层重试会让退避时间和取消语义都变得难以推理。保持 `maxRetries: 0`。
- 现有实现"已发出任何事件后不再重试"是正确的（避免向 UI 重复推送 delta），不要改。

**测试**：selector 单测断言返回值是 `RetryingModelGateway` 实例；补一个"首次 429、第二次成功"的用例验证端到端重试生效。

**预计工作量**：半天以内。

### 方案 C　激活上下文管理（对应 P0-3）

依赖方案 A —— 单回合场景下历史裁剪没有意义。建议在方案 A 落地后紧接着做。

#### C.1 实现生产 Token 计数器

`packages/core` 不能依赖具体分词器（会引入 vendor 耦合，违反边界约束），所以分两层：

**核心层**放一个确定性的启发式实现：

```ts
// packages/core/src/heuristic-token-counter.ts
const bytesPerToken = 4;
const perMessageOverheadTokens = 4;

export class HeuristicModelMessageTokenCounter implements ModelMessageTokenCounter {
  count(message: ModelMessage): number {
    const text = serializeForCounting(message);   // 含工具名、参数 JSON、结果
    const bytes = Buffer.byteLength?.(text) ?? new TextEncoder().encode(text).length;
    return Math.ceil(bytes / bytesPerToken) + perMessageOverheadTokens;
  }
}
```

用 **UTF-8 字节数**而不是字符数，能显著改善 CJK 的低估问题（一个汉字 3 字节 ≈ 0.75 token，接近真实值；而按字符数算是 0.25 token，偏差 3 倍）。注意 `packages/core` 不应引用 Node 的 `Buffer`，用 `TextEncoder` 即可。

同时把 `external-resource-context.ts:46-48` 的字符数估算换成同一个计数器，消除两套口径。

**留出精确计数的注入点**：`AgentRuntimeOptions.tokenCounter` 可选，宿主未来可以注入基于 `js-tiktoken` 的实现而不改 core。当前不引入这个依赖。

#### C.2 消费 usage 事件

在 `#streamModel` 中增加分支，把 Provider 报告的真实 token 用量记录到会话事件，并透出到 UI：

```ts
case "usage":
  this.#eventSink.emit({
    type: "agent.usage",
    sessionId,
    inputTokens: event.usage.inputTokens,
    outputTokens: event.usage.outputTokens,
  });
  break;
```

这需要在 `protocol` 增加对应 DTO 和 Webview 消息。收益有三个：用户能看到成本；可以用真实值校准启发式计数器；上下文接近上限时能提前预警。

#### C.3 接上溢出恢复

在 `AgentRuntime` 捕获 `ModelGatewayError` 时，识别上下文溢出（Provider 通常返回 `invalid-request` 且消息含 context length 相关文案），调用 `recoverFromContextOverflow` 后重试一次；仍失败则透出明确错误。

需要注意错误码粒度：当前 `invalid-request` 是个大类，溢出和"参数非法"混在一起。建议在 `packages/providers/src/ai-sdk-model-gateway.ts` 的错误映射里新增 `context-overflow` 码，避免用文案匹配做控制流。这是公共契约变更，需要先更新 `docs/architecture.md`。

#### C.4 处理截断

`finish.reason === "length"` 应当作为独立结果：

```ts
if (finish.reason === "length") {
  throw new TruncatedModelResponseError(toolSteps);
}
```

UI 上提示"模型输出被长度限制截断"，而不是把半截内容当成正常回答。

### 方案 D　补齐 Provider 上手路径（对应 P1-1、P1-3）

分两步，第一步是止血，第二步是体验。

#### D.1 泛化密钥保存命令

把现有的 `registerGeminiApiKeyCommand` 抽象成参数化实现，注册三个命令：

```ts
// apps/extension/src/commands/save-api-key.ts
const providers = [
  { id: "gemini", command: "ctrlZebra.saveGeminiApiKey", title: "Save Gemini API Key" },
  { id: "openai", command: "ctrlZebra.saveOpenAIApiKey", title: "Save OpenAI API Key" },
  {
    id: "openai-compatible",
    command: "ctrlZebra.saveOpenAICompatibleApiKey",
    title: "Save OpenAI-Compatible API Key",
  },

```

保持现有的密码遮蔽输入、SecretStorage 写入和"不回显"的处理方式不变，只是复制到另外两个 provider。同步更新 `apps/extension/package.json` 的 `contributes.commands` 和 README 的已知限制章节。

**工作量**：一天以内，无架构影响。

#### D.2 增加模型选择与配置引导

最小可行方案是一个 Quick Pick 命令 `ctrlZebra.selectModel`：

1. 读当前 `provider.id`；
2. 对 OpenAI / Gemini 调用各自的 list-models 接口拉取可用模型（两家 SDK 都支持），OpenAI-compatible 则请求 `{endpoint}/models`；
3. Quick Pick 让用户选，写回 `ctrlZebra.provider.model` 设置。

拉取失败时降级为手动输入框，不要阻断。**注意**：这会引入一次网络请求，需要在 `PRIVACY.md` 里说明"模型列表请求会向所配置的 Provider 发送一次不含工作区内容的请求"。

更完整的方案是在 Webview 里做一个 Provider 配置面板（选 provider、填 endpoint、存密钥、选模型、连通性测试），体验最好，但工作量是 Quick Pick 的三四倍。**建议先做 Quick Pick**，等有真实用户反馈再决定要不要做面板。

此外，当 `provider.model` 为空时，Webview 的 `OnboardingCard` 应当直接给出"选择模型"和"保存密钥"两个按钮，而不是只显示一段说明文字 —— 这是当前空状态最大的浪费。

### 方案 F　更换 Markdown 渲染器（对应 P1-5）

手写解析器要补齐标题、链接、表格、强调、有序列表、引用块，工作量和风险都高于直接换库。

**推荐 `markdown-it`**，配置为最严格模式：

```ts
import MarkdownIt from "markdown-it";

const md = new MarkdownIt({
  html: false,        // 关键：不透传任何原始 HTML
  linkify: false,     // 不自动把裸 URL 变成链接
  breaks: true,
});
```

`html: false` 之后模型输出无法注入 HTML，配合 Webview 现有的 nonce CSP（`apps/extension/src/agent-view.ts:57-63`，无 inline script），不需要额外引入 DOMPurify。但**仍需处理链接**：自定义 `link_open` 规则，只允许 `http`/`https` 协议，并且不直接在 Webview 内导航，而是通过既有的消息通道让 Extension 调 `vscode.env.openExternal`。这一点必须写进 `docs/security.md`。

代码块的复制按钮和现有样式需要迁移到新的渲染管线上，用 `md.renderer.rules.fence` 覆盖。

**风险**：这是给 Webview 引入的第一个运行时依赖，会增大 bundle。`markdown-it` 约 100KB（未压缩），对侧边栏面板可接受。按 `AGENTS.md` 第 4.2 节，新增依赖需要明确用例和负责人 —— 本方案的用例是"模型输出的技术说明当前无法正确显示"。

### 方案 I　MCP 生态兼容性（对应 P1-2）

这是本文档中唯一一个**推翻既有 ADR 决策**的方案，因此变更控制的要求最高。它也是唯一一个"要不要做"本身就需要产品判断的方案 —— 下面先给判断依据，再给实施路径。

#### I.1 两条独立的改造线与优先级

P1-2 的两道筛子成因不同，修法也不同，**不要当成一件事来排期**：

| 线 | 内容 | 是否推翻 ADR | 相对成本 | 建议 |
|---|---|---|---|---|
| **纪元线**（I.2–I.5） | 支持 legacy MCP 协议 | 是，需 ADR 0002 | 高（第二套生命周期 + 安全评审） | 先做产品判断 |
| **Schema 线**（I.6–I.7） | 放宽关键字白名单、降级到单工具粒度 | 否，属细化既有约束 | 低（单包内，不改生命周期） | **建议直接做** |

Schema 线值得优先，理由有三：它不触及连接生命周期因而安全评审面小得多；它不依赖任何产品判断（放宽的都是本就不构成安全边界的约束）；而且其中的"单工具粒度降级"（I.7）即便一个白名单关键字都不改，也能把"一个服务器全废"变成"少一个工具"，是整个方案 I 里性价比最高的单点改动。

如果最终决定不做纪元降级，Schema 线仍应独立执行。

#### I.2 纪元线：要不要做

| 如果…… | 那么 |
|---|---|
| MCP 是希望用户**现在就能用**的功能 | **必须做**。否则阶段 14 的 9 个任务、约 5,000 行代码对真实用户等于不可用 |
| MCP 是前瞻性押注，可以等生态跟上 | 现状可以保留。规范给了 legacy 至少 12 个月下线窗口，但主流服务器迁移完成的时间点无法预测 |

倾向前者。理由是投入产出严重失衡：已经付出了完整的实现成本，却因为一个配置层面的取舍而拿不到任何实际可用性。而且这个取舍不是不可逆的 —— 它本来就设计成可以扩展的（ADR 原话是"Expanding the matrix is an explicit product decision with fixtures"）。

#### I.3 纪元线：不要用 `auto` 模式

直觉方案是把 `versionNegotiation.mode` 从 `{ pin }` 改成 `'auto'`，让 SDK 自动探测降级。**对 CtrlZebra 这个具体架构不成立**，原因在 SDK 文档的这段限定里：

> On the SDK's stdio transport (**the base `StdioClientTransport` exactly**; subclasses probe in place) the probe runs on a short-lived sibling process spawned from the same parameters ... so a child that exits on the unrecognized probe, the shape of servers built on SDKs that terminate on any pre-`initialize` request, is simply a legacy server. A mid-probe connection close on HTTP (**or on a custom stdio-shaped transport, which probes in place**) rejects with the typed connect error.

`auto` 的优雅降级依赖一个技巧：先另起一个一次性的兄弟进程做探测，探测把它打死也无所谓，真正的连接用干净的新进程。**这个技巧只对 SDK 自带的 `StdioClientTransport` 生效。**

而 CtrlZebra 刻意不用那个类 —— ADR 0001 说明了原因：它自己管 spawn 和直接子进程的信号清理，会绕开宿主的启动审批和完整进程树生命周期。项目用的是自定义的 `SdkStdioTransport`（`packages/mcp-client/src/sdk-stdio-transport.ts`）跑在 Extension 拥有的进程端口上，属于文档所说的 "custom stdio-shaped transport"，**只能原地探测**。结果是：遇到收到无法识别的 `server/discover` 就退出的 legacy 服务器（文档指出这正是用旧 SDK 构建的服务器的典型行为），进程已死，`auto` 只会报连接错误，降不下去。

强行让 `auto` 工作需要自己实现两阶段 spawn（先起探测进程再起正式进程），这既要重新过一遍启动审批语义（用户批准的是一个进程还是两个？），也和"一个连接一个 generation"的现有模型冲突。不值得。

#### I.4 纪元线：推荐显式配置纪元 + `prior` 跳过探测

SDK 的 `Client.connect()` 有一个 `prior` 参数，优先级高于 `versionNegotiation`：

```ts
type PriorDiscovery =
  | { kind: 'modern'; discover: DiscoverResult }   // 复用已知的 discover 结果，零往返
  | { kind: 'legacy' };                            // 跳过探测，直接走 legacy initialize 握手
```

`{ kind: 'legacy' }` 完全不探测、不多起进程、行为确定。配置上给 `ctrlZebra.mcp.server` 增加一个可选字段：

```json
{
  "ctrlZebra.mcp.server": {
    "version": 1,
    "serverId": "local_docs",
    "displayName": "Local docs",
    "command": "/absolute/path/to/the-server",
    "args": ["--stdio"],
    "era": "legacy"
  }
}
```

`era` 取值 `"modern"`（默认，保持现有 `pin` 行为）或 `"legacy"`。连接时据此选择：

```ts
// packages/mcp-client/src/controlled-mcp-client.ts
const connectOptions =
  configuration.era === "legacy" ? { prior: { kind: "legacy" as const } } : {};
await this.sdkClient.connect(this.transport, { ...connectOptions, signal });
```

选它而不是 `auto` 的三个理由：

1. **与既有设计哲学一致**。整个 MCP 模块的原则是"用户显式配置、不自动下载、不自动安装、不自动连接、不自动重连、不自动重试"。探测式自动降级恰恰是这套原则要排除的那类隐式行为，而显式声明纪元完全在原则之内。
2. **规避自定义 transport 原地探测的死结**（见 I.3）。
3. **可测试性好**。两条路径都是确定的，不依赖"服务器会不会在探测时崩溃"这种时序行为，可以用固定 fixture 覆盖。

代价是用户需要知道自己的服务器属于哪个纪元。缓解办法：连接失败时给出精准提示（见 I.8），让用户一次就能改对。

#### I.5 纪元线：需要处理的实现面

**好消息**：业务原语的 API 在两个纪元下是统一的。`listTools` / `callTool` / `listResources` / `listResourceTemplates` / `readResource` / `listPrompts` / `getPrompt` 都由 SDK 抽象掉了，工具、资源、提示词三块的适配代码、限额校验、Schema 校验、审批绑定**基本不用动**。这是成本可控的主要原因。

**需要改的**：

| 位置 | 改动 |
|---|---|
| `packages/mcp-client/src/contracts.ts` | `mcpProtocolVersion` 单常量改为纪元 → 版本集合的映射 |
| `packages/mcp-client/src/sdk-options.ts` | `supportedProtocolVersions` 与 `versionNegotiation` 按纪元分支 |
| `packages/mcp-client/src/controlled-mcp-client.ts:411` | 硬编码的版本相等判断改为按纪元校验协商结果 |
| 同上，连接流程 | modern 是 `server/discover → connected`；legacy 是 `initialize → notifications/initialized → connected`，两条生命周期都要能被 generation 模型正确关闭 |
| `apps/extension/src/adapters/mcp-server-configuration.ts` | 解析并校验新的 `era` 字段 |
| `apps/extension/package.json` | 配置 Schema 增加 `era` 枚举与描述 |

**必须做安全评审的三处**（整套 MCP 安全姿态是照着 modern 生命周期设计的）：

1. **服务器发起的请求**。legacy 纪元下服务器可以主动向客户端发 sampling / roots / elicitation 请求，modern 用 `InputRequiredResult` 取代了这套。项目声明了空 capabilities 且 `enforceStrictCapabilities: true`，理论上会被拒绝，但这是一条**当前完全没有测试覆盖的新路径**，必须补齐拒绝行为的断言。
2. **通知语义差异**。SDK 文档指出 2025 纪元的非请求式通知在 legacy 连接上的触发方式不同，`tools/list_changed` 等刷新逻辑需要在两个纪元下分别验证。
3. **会话概念回归**。legacy 在 stdio 上把语义绑定到进程，与项目"一个连接一个 generation、断开即作废"的模型需要确认没有冲突。

#### I.6 Schema 线：区分"危险"与"未建模"

把当前单一的白名单拆成两类处置。

**必须拒绝**（保持现状，这些是真实攻击面）：`pattern`、`patternProperties`（服务器提供的正则编译进 Ajv 后用模型生成的参数执行 → ReDoS）、非本地 `$ref`（SSRF）、以及超出深度/节点/属性/字节限额的结构（DoS）。

**改为静默剥离**（记入本地结构化日志，不影响工具可用性）：`format`、`$id`、`$comment`、`readOnly`、`writeOnly`、`deprecated`、`nullable`、`if` / `then` / `else`、`dependentSchemas`、`dependentRequired`、`propertyNames`、`contains` / `minContains` / `maxContains`、`unevaluatedProperties` / `unevaluatedItems`、`contentEncoding` / `contentMediaType` / `contentSchema`。

**改为改名映射**：`definitions` → `$defs`，同时接受 `#/definitions/...` 形式的 `$ref` 并重写为 `#/$defs/...`。只剥离不改名会让指向它的引用悬空，反而触发 `assertAcyclicReferences` 的解析失败。

剥离约束在这个架构下是安全的，理由有三点，需要在 `docs/security.md` 里写清楚：

1. `format` 在 Draft 2020-12 中默认是**注解**语义，未启用 format-assertion 词汇表时不产生断言效果，剥离它不损失任何已生效的校验；
2. 剥离一条约束只意味着 CtrlZebra 校验得更宽松，而 **MCP 服务器自身会再校验一遍**并拒绝非法参数；
3. 更关键的是，每次 MCP 工具调用都要走一次性人工审批，审批卡展示的是**实际将要发送的参数**。真正的安全边界在审批，不在 Schema。

因此放宽 Schema 不会导致未经批准的副作用，最坏情况只是模型多试错一轮。用整个工具目录不可用去换取一点校验严格度，这笔账是亏的。

实现上建议在 `walkSchema` 里把当前的 `allowedKeywords` 单集合改为三个集合（`allowedKeywords` / `strippedKeywords` / `rejectedKeywords`），未出现在任何集合中的未知关键字**继续拒绝** —— 保留"闭合集合"这一设计，只是把已知无害项从拒绝挪到剥离。

#### I.7 Schema 线：降级到单工具粒度

这是方案 I 里性价比最高的单点改动，且与 I.6 相互独立。

`createMcpToolSnapshot` 目前遇到第一个不合规 Schema 就终止整个快照构建（`packages/mcp-client/src/mcp-tool-snapshot.ts:146-155`）。改为逐工具收集结果：

```ts
// packages/mcp-client/src/mcp-tool-snapshot.ts
const usable: McpToolDescriptor[] = [];
const rejected: { readonly toolName: string; readonly reason: McpSchemaRejectionReason }[] = [];

for (const record of records) {
  try {
    usable.push(buildDescriptor(record));
  } catch (error) {
    if (error instanceof McpToolSchemaError) {
      rejected.push({ toolName: record.name, reason: error.reason });
      continue;
    }
    throw error;
  }
}
```

配套约束：

- `McpToolSchemaError` 需要携带一个**枚举化**的拒绝原因（如 `"forbidden-keyword"` / `"limit-exceeded"` / `"non-object-root"`），不能带服务器原始字符串；
- 快照视图增加 `rejectedTools` 列表，经 Protocol 投影到 Webview，在 MCP 面板里列出被跳过的工具及原因；
- **全部工具都被拒时仍应视为失败**（返回现有的 `invalid-schema` 错误），否则用户会看到一个空目录却不知道原因；
- `malformed-message`（重名、保留名、结构非法）与 `invalid-schema` 的处置要区分开：前者说明服务器行为异常，维持整体失败更合适。

#### I.8 错误信息可操作（两条线共用）

把失败提示从笼统改为可操作。当前是：

```5:5:packages/mcp-client/src/errors.ts
  "protocol-incompatible": "The MCP Server does not support the required protocol version.",
```

既然 legacy 服务器是当下压倒性的失败原因，提示应当点明纪元差异与处置办法，例如："This Server uses the legacy MCP protocol (2025-11-25 or earlier). CtrlZebra requires 2026-07-28." 做了方案 I 之后再补一句指引用户设置 `era: "legacy"`。

Schema 侧同理。当前无论因为哪种原因被拒，用户都只看到 `"MCP Tool schema is invalid or unsupported."`，既不知道是哪个工具也不知道是哪个关键字。配合 I.7 的单工具降级，应当在 MCP 面板列出被跳过的工具及枚举化的原因。

注意 `docs/protocol.md:210` 约束了 `McpErrorDto.message` 是不超过 1,024 码点的固定用户安全字符串，且禁止透出原始 JSON-RPC 码、SDK 错误和进程细节。**新文案必须保持这个约束**：协议侧不能把服务器返回的版本号原样拼进去；Schema 侧的关键字名必须取自 CtrlZebra 自己的白名单枚举，不能回显服务器提供的字符串。工具名本身可以展示，但要沿用既有的长度与 Unicode 良构校验。

## 7. 能力路线建议

第 5、6 节处理的是"已建成的东西为什么没产生价值"。本节处理另一个问题：**补齐之后往哪走**。

内容源于一次关于 Skills、Session context、ReAct、Plan-and-Solve 和多 Agent 的规划讨论。与前面各节不同，这里的判断带有更强的主观成分，且**没有一项是当前可以立即动手的** —— 全部压在阶段 15 之上。

### 7.1 三处需要重新定性

在排优先级之前，有三个提法建议先调整，否则会把已有的东西重做一遍，或者把不同性质的工作混在一起。

**「Session context 管理」不是未来项。** 这个说法通常混着三件事：

| 层次 | 现状 | 归属 |
|---|---|---|
| 单会话内的多轮上下文 | 完全不存在（每条消息一个新 Session） | **P0-1，阶段 15** |
| 历史裁剪与摘要压缩 | 代码齐全但无生产调用方 | **P0-3，阶段 15** |
| 跨会话记忆 | 不存在 | 真正的未来项，见 7.2.5 |

前两层是其他一切的前提，不该进未来规划。只有第三层是新能力。

**「引入 ReAct 范式」是重复建设。** 当前运行循环已经是：模型流式输出 → 发出 Tool Call → 执行 → 结果 append 回 `messages` → 再次调模型。这在结构上就是 ReAct（推理与行动交替），阶段 13 的 reasoning summary 通道则是 "Thought" 的现代等价物。

原始 ReAct 论文的 `Thought:` / `Action:` / `Observation:` 文本脚手架，是为**没有原生 function calling 的模型**设计的补丁。在支持原生工具调用的模型上引入它，等于用文本解析替代结构化协议，是倒退。

真正卡住能力的是循环约束而非范式：

```322:327:packages/core/src/agent-runtime.ts
        if (toolCall !== undefined) {
          throw new Error("AgentRuntime supports only one Tool Call per model response.");
        }
        if (toolSteps >= this.#maxToolSteps) {
          throw new MaxToolStepsExceededError(this.#maxToolSteps);
        }
```

建议改写为「放宽循环约束 + 增加失败反思」，详见 7.2.3。

**「Skills」建议先落到「项目级规则文件」。** 路线图候选清单第 4 项已有"项目级规则文件"，Skills 是它的超集。先做简单版验证不可信指令的处理模式，再扩展到多技能渐进加载，详见 7.2.4。

### 7.2 各项落地要点

#### 7.2.1 评测基线（清单中缺失，但应排第一）

这是本节最重要的补充。**打算改 Agent 策略，就必须能测量改动是变好还是变坏。**

项目现有 1195 个单元测试，纪律很好，但它们测的全是"函数行为正确"，没有一个测的是"**Agent 完成任务的能力**"。而 7.2.2 和 7.2.3 都会显著改变 Agent 行为，这类改动**无法靠单元测试和手工试用判断**——手工试十次的样本量说明不了任何问题，而且人会不自觉地只试自己设计时想到的场景。

建议规模：20–30 个任务，包含固定的 fixture 工作区、任务描述和**确定性判分**（产出文件内容是否符合预期、命令退出码、是否调用了不该调的工具、步数与 token 消耗）。用便宜模型跑，做成一条本地命令；进 CI 需要 API Key，可作为可选 job 或定期任务。

关键设计约束：判分必须确定性，不要用"模型给模型打分"作为主判据——那会引入一个无法回归的评判者。模型判分只适合作为辅助指标。

这一项还有个副产品：它会倒逼 7.2.3 的 usage 事件透出（方案 C.2）落地，因为 token 消耗是核心评测指标之一。

#### 7.2.2 Plan/Act 模式

四项里用户价值最高的，且**已在路线图候选清单第 3 项**（"Plan/Act 模式，验证 Tool Policy 可配置性"）。

它与 CtrlZebra 的产品哲学契合度极高，这是最值得强调的一点。整个项目的核心是"昂贵或不可逆的动作之前必须有一次可审阅的人工确认"，而**计划恰好是一个廉价的、可审阅的产物**，位于一堆文件修改和命令执行之前。当前用户只能逐个审批 `propose_file_edit`，看不到全局意图；有了计划，用户可以在任何文件被触碰之前否决整个方向。这等于把既有审批机制从**操作级提升到意图级**，收益大于单纯增加能力。

落地要点：

- 计划是一等持久化实体，能随 Session 恢复；
- 计划本身可审批，复用既有的单次审批语义；
- 计划与后续执行有绑定关系，计划变更使已有批准失效；
- 执行失败后能重新规划，且重新规划需要新的确认；
- Plan 模式下工具策略收紧为只读，这正是路线图所说的"验证 Tool Policy 可配置性"。

**不要过早抽象。** 很容易想到做一个 `AgentStrategy` 接口让 ReAct 和 Plan-and-Solve 各成一个实现，但 `AGENTS.md` 第 4.2 节明确禁止"无当前用例的抽象"，而且这类学术范式淘汰很快（Reflexion、Tree-of-Thoughts、Self-Refine 都火过）。正确顺序是**先把 Plan 模式作为第二个具体模式实现出来，等两个实现真的并存了再抽接口**。

#### 7.2.3 放宽循环约束与失败反思

替代"引入 ReAct"的具体内容：

| 改动 | 现状 | 说明 |
|---|---|---|
| 单响应多 Tool Call | `agent-runtime.ts:322-324` 抛错 | 现代模型会并行发起多个读操作，这是显著的效率差异 |
| 提高步数上限 | `agent-runtime.ts:100` 为 8 | 需与上下文预算联动，不应是固定常量 |
| 失败反思 | 失败原因被通用文案覆盖（P2-2） | 让模型看到结构化失败原因并调整策略 |
| 工具门控 | 正则启发式（`agent-behavior-policy.ts:10-19`） | `"hi, fix the bug"` 类输入会误判，应改为模型自决 |

**顺序上有一处硬约束**：当前的 8 步限制事实上是个上下文保护装置——因为没有历史裁剪，步数一多必然撑爆上下文。**在方案 C 落地之前放宽它，只会把"步数超限"错误换成"上下文溢出"错误**，用户体感更差。

并行多 Tool Call 还有一个与审批相关的设计问题需要先定：一个响应里同时出现两个需要审批的操作时，是逐个审批、批量审批，还是拒绝这种组合？建议初版**只允许并行只读工具**，写/执行工具仍限制为每响应一个，这样完全不触动审批语义。

#### 7.2.4 项目级规则文件 → Skills

Skills 的本质是**渐进式披露**：有 N 个技能，只在相关时加载某一个的完整正文。因此它在上下文预算真正生效之前没法做对，这是第一个依赖。

第二个也是更重要的依赖：**技能文件是工作区内容，属于不可信输入**。用户克隆一个仓库，其中的技能文件是攻击者可控的文本，而它的作用恰恰是"改变 Agent 的行为指令"——这是典型的提示注入载体。

好消息是**项目已有现成的正确模式**。ADR 0001 处理 MCP Prompt 时的规定是：提示词文本只在用户完整预览并显式确认后，才作为**一条普通用户输入**进入流程；Server 声明的 role 只是溯源信息，永不获得 System 权威。Skills 应当套用同一模式：

- 技能正文永远不进 system instruction，只作为普通用户上下文；
- 首次使用某技能需要预览与确认；
- 技能不能声明自身拥有更高权限，更不能绕过或降低工具审批要求；
- 技能来源（用户级 / 工作区级）必须在 UI 上可见，工作区级默认更不受信任。

建议路径：先做单文件的项目约定（一次性加载、无渐进披露、无脚本执行），验证不可信指令的处理契约；再扩展到多技能渐进加载；技能附带可执行脚本是更后面的事，它会把"技能"变成一种新的代码执行入口，需要独立的安全契约。

#### 7.2.5 跨会话记忆

真正的新能力，但**也是最容易做砸的一项**。多数实现最后会变成一个悄悄污染上下文、用户既看不见也删不掉的黑盒。

对一个把"用户显式控制"当第一原则的项目，如果要做，记忆条目必须是**可列出、可编辑、可删除、注入时可见**的，而不是自动摘要后静默塞进 system prompt。这与项目对 Session、Checkpoint、MCP 附件的处理方式一致——它们全都是用户可见可操作的实体。

另外需要一个保留策略。P2-3 已经指出 Session 与 Checkpoint 目前没有自动清理策略也没有产品内删除入口，跨会话记忆会把这个问题放大，应当在同一批工作里一并解决。

#### 7.2.6 多 Agent

放在最后，路线图现有的门禁判断是对的：*"多 Agent 必须建立在可恢复 Session、确定性 Tool 生命周期和资源隔离之上。"* 以下是把这句话展开成可执行约束。

**先认清它的本质：多 Agent 主要是一种上下文隔离技术，不是智能技术。** 派生子 Agent 的核心收益是——花掉子 Agent 的 N 万 token 上下文，只向父 Agent 返回 500 token 的结论，从而让父上下文保持干净。并行只是次要收益。这意味着它在逻辑上**下游于上下文管理**：如果无法测量和预算上下文，就无法判断某次委派是否划算，多 Agent 只会变成"更快地烧掉上下文和预算"。

**最难的部分是审批模型，这是 CtrlZebra 特有的。** 项目的安全基石是"每个写/执行操作都需要一次绑定到确切操作的、单次有效的人工审批"。于是：

- 子 Agent 想写文件，谁来批？只能是用户。但 N 个并行子 Agent 会产生 N 路交错的审批请求，UX 直接崩塌；
- 更糟的是用户会开始**无脑点同意**，而这会摧毁整个审批机制的安全价值——这比功能不可用严重得多；
- 让父 Agent 代替用户批准是绝对不行的，ADR 0001 已经明确"Core 始终拥有全部 Agent 与 Tool 策略"，工具永不自我批准。

因此**初版应当限制子 Agent 只能使用只读工具**。一个只读的探索型子 Agent 需要零审批，却能带来主要的上下文隔离收益，且完全不触动安全模型。写和执行继续由主 Agent 在用户面前逐个审批。等到只读委派的价值被评测证实之后，再单独设计"可写子 Agent"的审批聚合方案。

**资源隔离的具体清单**（对应 `AGENTS.md` 第 3 节"长时工作必须接受 `AbortSignal`，定时器、监听器、流、进程、注册和未观测的 Promise 都需要明确所有者与幂等清理"）：

- 取消必须沿 Agent 树传播，父被取消时所有子必须终止，且不得有迟到事件影响 Core、持久化或 UI；
- 每个子 Agent 从父预算中**切分**出自己的 token 与步数配额，而不是各自独立拥有上限；
- 子 Agent 的工具注册、审批工作流、MCP generation 归属必须明确，断连或失去工作区信任时一并作废；
- 子 Agent 失败不应默认导致父失败，需要明确的失败传播语义。

**持久化建议**：把子 Agent 运行建模为**带父链接的子 Session**，而不是在父事件流里做嵌套事件。理由是现有 `SessionRecord` 是扁平事件流，扁平结构的可重放性和恢复逻辑简单得多；嵌套会让 P0-1 里刚建好的历史重建逻辑复杂度陡增。

**UI 需求**：当前转录区是扁平的 `<ol>`，需要可折叠的嵌套运行视图，且子 Agent 的 token 消耗要能单独看到——否则用户完全无法理解账单。

**与 Plan 模式的关系值得注意**：一个包含若干独立步骤的计划，恰好就是让委派变得可处理的结构。先做 Plan 模式，多 Agent 就从"另一种范式"退化成"在隔离上下文中执行计划步骤"，实现和心智负担都小很多。**这是把 Plan 排在多 Agent 之前的重要理由。**

最后，多 Agent 的收益高度依赖任务类型，不少产品加上之后结果更差、成本更高。**它必须被评测基线（7.2.1）证实有效之后才值得保留**，这是所有能力项里最需要用数据说话的一项。

## 8. 功能缺口：IDE 集成与工具集

第 4 节讲的是"已建成的能力没接上线"，第 7 节讲的是"未来能力怎么排序"。本节是第三类问题：**有一批基础功能既没有建成，也不在任何现有规划里**——它们不在路线图候选清单中，也不在第 7 节讨论的范围内。其中 8.1 一项，我认为优先级高于第 7 节的全部内容。

### 8.1 编辑器感知为零（本节最大缺口）

对全仓源码（排除测试）检索的结果：

| VS Code 能力 | 典型用途 | 引用数 |
|---|---|---|
| `activeTextEditor`、`visibleTextEditors`、选区、`onDidChangeActiveTextEditor` | 知道用户正在看哪个文件、选中了哪段代码 | **0** |
| `languages.getDiagnostics()` | 读取编译错误、类型错误、lint 警告 | **0** |
| `executeDefinitionProvider`、`executeReferenceProvider`、`executeDocumentSymbolProvider`、`executeWorkspaceSymbolProvider` | 跳转定义、查找引用、列出符号 | **0** |
| 编辑器右键菜单、Code Action、选中即问的快捷键 | 从代码位置发起对话 | `package.json` 无相关贡献点 |

也就是说，Agent 完全不知道用户此刻在做什么。三个具体后果：

1. **指代失效**。用户光标停在报错的函数上问"这里为什么错了"，Agent 不知道"这里"是哪里，只能用 `search_files` 去猜。
2. **改代码没有反馈回路**。Agent 想确认自己改完有没有编译错误，唯一途径是 `run_command` 跑一次构建再解析 stdout——慢、费 token、要过审批，而且输出是非结构化的。而 VS Code 里这份信息是现成、实时、结构化的。这一条对 Agent 的实际质量影响最大：**有诊断反馈的修改是闭环的，没有的是盲改**。
3. **入口只有一个**。只能在面板里打字，无法从代码位置直接发起。

这个缺口的严重性在于它动摇了产品形态本身：**把 CtrlZebra 整体搬到终端里运行，几乎不损失任何能力**。既然如此，做成 VS Code 扩展的理由就只剩下"渲染方便"了。第 7 节讨论的 Plan 模式、Skills、多 Agent 都是"让 Agent 更聪明"，而本节是"让 Agent 知道自己在哪"——后者是前者的地基。

**一个推论：接入 LSP 之后，路线图候选清单第 6 项"代码语义索引"大概率不必要。** 自建语义/向量索引是个大工程，需要处理增量更新、多语言解析、召回质量评估，而且效果不稳定；VS Code 的语言服务器已经提供准确、实时、跨语言的定义/引用/符号能力，直接通过 `vscode.commands.executeCommand` 调用即可。建议把候选第 6 项**降级或直接替换**为"LSP 能力工具化"，这是本次评估中投入产出比最高的一处方向调整。

### 8.2 工具集不完整

#### 8.2.1 无法创建、删除、重命名文件

`packages/builtin-tools/src` 下没有任何创建、删除或重命名文件的工具。`propose_file_edit` 只能对**已存在**的文件做范围替换——`apps/extension/src/adapters/workspace-edit-applier.ts` 的依赖接口里只有 `replace`，且执行前必须先 `openTextDocument`，`WorkspaceEdit` 的 `createFile` / `deleteFile` / `renameFile` 都没有使用。

后果是"新建一个测试文件"这类最基本的编码任务，Agent 现在**做不到**。这不是体验问题，是硬功能缺失。本节中它与 8.1 的编辑器上下文、诊断信息同属"任何对外发布之前都必须补齐"的一档（见第 9.2 节门槛清单第 3、8 项）。

#### 8.2.2 编辑是单文件的，而且没有原子性

`proposeFileEditInputSchema` 只接受一个 `path`（`packages/builtin-tools/src/propose-file-edit.ts:44`）。跨文件重构因此要拆成 N 次工具调用、N 次审批，并且：

- **没有原子性**——改到第 3 个文件失败时，前 2 个已经落盘；
- **回滚粒度也是单文件**——checkpoint 按单个 `plan.uri` 记录（`workspace-edit-applier.ts:92-94`），无法一次撤销整组改动；
- **叠加"一次模型响应只允许一个工具调用"的限制**（P1-6），一个 5 文件的重构至少需要 5 个模型往返。

这三条是同一个约束的三个侧面，应当一并处理。

#### 8.2.3 搜索只支持精确子串

`search_files` 的 `query` 字段描述是 `"Exact text to search for."`，实现走的是纯子串匹配，不支持正则。"找出所有 `use` 开头的 hook"这类需求无法表达，Agent 只能退化成多次猜测式搜索。

值得肯定的是**截断处理做对了**：扫描文件数超限、单文件字节超限、结果数超限三种情况都会置 `truncated` 标志并透出，Agent 能知道结果不完整。这一点比很多同类实现严谨。

### 8.3 对话交互缺基础件

全仓没有 `regenerate` / `editMessage` / `resend` / `mention` 相关实现。具体缺失：

- 不能编辑历史消息后重新发送；
- 不能重新生成上一条回复；
- 不能在 Agent 运行过程中插话纠偏——只能取消，而取消会丢掉整个 run；
- 不能用 `@` 引用工作区文件（MCP 资源可以附加进上下文，工作区文件反而不行，这个不对称有点反直觉）。

这些在任何成熟的 AI 对话界面里都属于默认功能。需要说明的是，**会话列表与恢复是有的**（`apps/webview/src/vscode-api.ts` 的 `listSessions` / `restoreSession` / `restoreCheckpoint`），这块不缺。

### 8.4 无多模态输入

`ModelMessage` 是 `ModelTextMessage`（`content: string`，`packages/core/src/model-gateway.ts:7-10`）、工具调用与工具结果三者的联合类型，没有任何图片或二进制变体。用户贴报错截图、贴 UI 设计稿是很高频的用法，目前走不通；MCP 那一侧也明确排除了二进制内容（ADR 0001 兼容性矩阵："Images, audio, Blob, embedded Resource, Resource Link → Rejected as unsupported"）。这项改动会穿透协议、Core、Provider 和 Webview 四层，成本不低，建议放到 GA 之后。

### 8.5 一处澄清：token 用量是采集了的，丢在运行时

需要澄清一个容易得出的错误印象：**`TokenUsage`（`inputTokens` / `outputTokens` / `totalTokens`）已经在 Provider 层采集并作为流事件发出**（`packages/providers/src/ai-sdk-model-gateway.ts`）。

数据断在运行时而非界面：`AgentRuntime.#streamModel` 里没有 `usage` 分支，事件被静默丢弃（P0-3 的最后一段），因此 `packages/protocol` 里根本不存在 `usage` 字段，数据从来没有机会到达 Webview。换句话说，缺的是**运行时的一个 case 分支加一条协议字段**，不是采集能力。

这属于第 4 节反复出现的那个模式——**建成了但没接线**，而不是功能缺失。第 6.1 节的 T1506「消费 usage 事件并透出到 UI」已经覆盖这一项，本节不重复提出。

### 8.6 实施方案

#### 方案 J　IDE 集成（对应 8.1）

分四步，每步独立可交付；J.1、J.2 是发布门槛，J.3、J.4 可后置：

**J.1 编辑器上下文（最小集）**——新增一个 host adapter 读取活动编辑器路径、选区范围与选区文本，作为可选的上下文片段注入 system prompt。需要注意三点：路径必须经过与 `propose_file_edit` 相同的工作区边界校验；选区文本要计入 token 预算（复用 `filesTokenBudget` 的口径）；用户必须能关闭这项注入（隐私考量，`PRIVACY.md` 需同步）。

**J.2 诊断信息工具**——新增只读工具 `get_diagnostics`，参数为可选的 `path`，返回结构化的 severity / 范围 / 消息 / 来源。风险等级 `read`，无需审批。这一项是整个方案 J 里性价比最高的，因为它把"改完代码不知道对不对"变成了闭环。需要设定结果数上限并复用 `truncated` 机制。

**J.3 LSP 能力工具化**——新增 `find_definition`、`find_references`、`list_symbols` 三个只读工具，内部调用对应的 `execute*Provider` 命令。同时按 8.1 的推论重新评估路线图候选第 6 项。

**J.4 编辑器入口**——在 `package.json` 增加右键菜单贡献点与"选中内容发起提问"的命令。依赖 J.1。

#### 方案 K　文件生命周期与多文件编辑（对应 8.2）

**K.1 文件生命周期工具**——新增 `propose_file_create` 与 `propose_file_delete`，风险等级 `write`（`ToolRisk` 枚举只有 `read` / `write` / `execute` / `network` 四值，没有单独的删除等级），走与 `propose_file_edit` 相同的审批与 checkpoint 路径。删除操作的 checkpoint 必须保存完整原文，否则无法回滚。

**K.2 多文件原子编辑**——把 `propose_file_edit` 的输入从单个 `path` 改为文件数组，或新增 `propose_workspace_edit`。VS Code 的 `WorkspaceEdit` 本身就支持跨文件原子应用，改造主要在 Schema、审批 UI（需要按文件分组展示 diff）和 checkpoint 结构（`files` 数组已经是复数形式，改动不大）。这项应当与 P1-6 的"放宽单工具调用限制"一并考虑。

**K.3 搜索支持正则**——`search_files` 增加可选的 `isRegex` 参数。必须使用带超时/步数上限的匹配实现以防 ReDoS，或对模式做复杂度校验后拒绝危险模式。

#### 方案 L　对话交互基础件（对应 8.3）

重新生成、编辑重发、`@` 文件引用。这三项都依赖阶段 15 的多轮对话契约——因为它们本质上都是"对历史消息做修改后重新推进"，在单轮模型下无从谈起。因此方案 L 必须排在阶段 15 之后，不能提前。

### 8.7 与第 7 节的优先级关系

我的判断是**方案 J、K 应当插到第 7 节全部内容之前**，理由有三条：

1. **它是差异化的来源**。终端形态的编码 Agent 已经很多，IDE 集成是这个形态存在的理由。
2. **它对 Agent 质量的提升是杠杆式的**。诊断反馈让改代码从盲改变成闭环，LSP 让查找引用从 grep 猜测变成准确定位——这两项对输出质量的影响，很可能超过 Plan 模式或多 Agent。
3. **成本低**。VS Code API 都是现成的，不需要自建索引、不需要新的信任模型、不需要 ADR（K.1 涉及新的写操作风险，需要走安全评审，但不需要新架构决策）。

因此建议的阶段编号是：**阶段 19 = 方案 J（IDE 集成）**，**阶段 20 = 方案 K（文件生命周期与多文件编辑）**，第 7.3 节表格中原定的阶段 19–25 顺延为 21–27，方案 L 并入阶段 21 之后的界面工作。

## 9. GA 就绪度评估

### 9.1 先把 GA 的含义定清楚

"完成规划后能不能 GA"这个问题，需要先明确 GA 对一个 VS Code 扩展意味着什么。它不只是"功能做完了"，而是一组承诺：**装了就能用、升级不丢数据、出问题能诊断、坏了有人修**。功能完备只是其中一条。

因此我的建议是**不要直接奔向 GA，先在 Marketplace 发 Preview**。Preview 的门槛低得多（大致对应 9.2 表格中标记为「Preview」的行），能提前拿到真实用户的失败模式——尤其是 MCP 生态兼容性（P1-2）和跨平台差异这两类问题，靠内部测试很难覆盖全。用 Preview 阶段收集到的数据再决定 GA 的时间点，比现在预设一个时间点更稳妥。

### 9.2 GA 门槛清单

以下每一项都标注了对应的既有方案编号，或标记为新增工作。「阶段」列表示该项是 Preview 就需要，还是 GA 才需要。

| # | 门槛 | 当前状态 | 对应工作 | 阶段 |
|---|---|---|---|---|
| 1 | 核心链路可用（多轮对话） | ❌ 单轮 | 阶段 15 | Preview |
| 2 | 默认 Provider 可配置 | ❌ OpenAI 无法保存 Key | 阶段 16 / 方案 D | Preview |
| 3 | 能创建文件 | ❌ 无此工具 | 方案 K.1 | Preview |
| 4 | 生产环境有重试 | ❌ 未接线 | 方案 B | Preview |
| 5 | **跨平台验证** | ❌ CI 仅 `ubuntu-latest` | **新增** | Preview |
| 6 | 界面语言统一 | ❌ 中英混杂 | 阶段 17 / 方案 E | Preview |
| 7 | MCP 能接上现存服务器 | ❌ 两道筛子 | 阶段 18 / 方案 I | Preview |
| 8 | 编辑器上下文与诊断 | ❌ 零感知 | 阶段 19 / 方案 J.1–J.2 | Preview |
| 9 | **会话删除与保留策略** | ❌ 项目已自认缺失 | **新增** | GA |

表中标记为**新增**的共六项（第 5、9、10、12、13、14 项），下面分五小节展开核实依据与要点，其中第 13、14 项合并说明。

#### 9.2.1 跨平台验证（第 5 项）

`.github/workflows/ci.yml` 和 `package-vsix.yml` 都只有 `runs-on: ubuntu-latest`，没有 matrix。对一个会 `run_command` 拉起子进程、大量处理文件路径的扩展来说，这个覆盖面不够：

- Windows 的路径分隔符、shell 差异（`cmd` / PowerShell）、进程终止语义都与 POSIX 不同，而 `docs/security.md` 里关于进程清理和终止确认的约定相当细致——这些约定在 Windows 上是否成立，目前没有任何证据；
- `propose_file_edit` 的路径校验正则显式拒绝反斜杠，Windows 上用户输入的路径形态需要验证；
- 换行符（CRLF）对文本编辑的范围计算有影响。

要做的事：CI 加 `matrix.os: [ubuntu-latest, windows-latest, macos-latest]`。这一项成本很低但发现问题的概率很高，建议尽早做，不必等到 Preview。

#### 9.2.2 会话删除与保留策略（第 9 项）

这一项项目自己已经记录在案，`README.md:182` 与 `PRIVACY.md:38` 都明确写着 Session 与 Checkpoint「没有自动清理策略，也没有产品内的删除控件」。

对一个把全部对话内容以明文存在本地的工具来说，**没有删除入口在 GA 阶段是站不住的**：用户可能在对话里粘贴过密钥、内部代码或客户数据。至少需要单个会话删除、全部清空，以及一个可配置的保留期。`vscode-api.ts` 已有 `listSessions`，加 `deleteSession` 的增量成本不大。

#### 9.2.3 数据格式迁移（第 10 项）

`docs/persistence.md` 把兼容性契约写得很清楚——不兼容变更需要新的版本目录、迁移不得原地修改源会话、新会话必须在全部数据文件与 manifest 提交成功后才可见。这套设计是对的。但同一份文档第 115 行也明确写着**自动迁移不在当前范围内**。

问题在于阶段 15 的多轮对话几乎必然改变会话数据形态。如果 Preview 用户的历史会话在升级后打不开，那是最伤信任的一类失败。GA 前需要：要么实现自动迁移，要么实现"旧版本会话只读打开"的降级路径并明确告知用户。

#### 9.2.4 成本护栏（第 12 项）

用量数据在 Provider 层已经采集（8.5），T1506 会把它接通并展示出来，但**展示不等于护栏**。多轮对话 + 上下文管理上线后，单次会话的 token 消耗会显著上升，而目前没有任何机制阻止一次失控的循环烧掉大量费用。最低限度需要单次 run 的 token 上限和超限时的中断提示。这一项依赖 T1505 的生产 token 计数器。

#### 9.2.5 诊断导出与发布流水线（第 13、14 项）

没有遥测是这个项目的产品选择，我认同。但代价是**用户报 bug 时你拿不到任何信息**。需要一个「导出诊断信息」命令，生成一份脱敏的本地报告（扩展版本、VS Code 版本、平台、Provider 类型不含 Key、MCP 服务器连接状态与失败码、最近的错误），由用户自行决定是否附在 issue 里。`docs/security.md:56` 关于诊断不得泄漏敏感内容的约束正好是这个功能的设计依据。

发布侧目前只有 `package-vsix.yml` 打包，没有发布 workflow。GA 前需要补：`vsce publish` 自动化、版本号与 CHANGELOG 的一致性校验、以及 Marketplace 页面所需的图标与截图素材。

### 9.3 功能上还缺什么

除第 8 节列出的之外，就 GA 的门槛而言，我认为**没有其他必须补齐的功能缺口**。第 7 节的 Plan 模式、Skills、跨会话记忆、多 Agent 都属于竞争力范畴而非成立性范畴——它们决定产品好不好，不决定产品成不成立。多模态（8.4）同理，虽然常用，但缺了不影响核心场景闭环。

需要强调的反而是第 15 项**评测基线**：它不是功能，但它是判断"上面这些改动到底有没有让 Agent 变好"的唯一手段。在没有基线的情况下推进阶段 19 之后的任何策略性改动，都只能靠感觉验收。

### 9.4 结论

按现在的规划全部完成（阶段 15–18 + 第 8 节的方案 J、K），项目会**达到 Preview 质量**——核心链路通、默认配置可用、能感知编辑器、MCP 能接上生态。这是一个可以放到 Marketplace 上收集真实反馈的状态。

**距离 GA 还差的主要不是功能，而是运维成熟度**：跨平台证据、会话删除、数据迁移、成本护栏、诊断导出、发布流水线这六项。加起来的工作量不算大——粗估在两到三周量级，远小于阶段 15 一个阶段——但它们无法通过写更多功能来绕过，而且每一项缺失都会在真实用户那里以最难堪的方式暴露出来。

时间顺序上的建议是：**第 9.2.1 项（CI 跨平台矩阵）现在就做**，不要等——它成本最低、发现问题的概率最高，而且越晚做，需要回头修的平台相关代码越多。

## 附：一句话结论

CtrlZebra 的**工程骨架和安全模型质量很高**，规范化程度超过绝大多数同类个人项目；真正的短板集中在**产品闭环**上 —— 没有多轮对话、默认 Provider 不可用、上下文管理写好了却没接线、MCP 接不上现存生态里的服务器。

值得注意的是，这四项**没有一项是设计缺陷**：前三项是接线缺口；第四项由两个独立原因叠加而成，一个是九天前还成立、如今已被生态现实推翻的协议版本取舍，另一个是把"没建模的 Schema 关键字"误当成"危险关键字"来拒绝、且失败粒度过粗。也就是说，这个项目已经建成的能力远多于它当前能交付的价值，补齐的投入产出比很高。

建议按第 6.2 节的顺序推进：先用半天接上重试层建立信心，再花一周补齐工程安全网，然后集中资源打通多轮对话；同时尽早对"是否支持 legacy MCP"做出产品判断，因为它决定了已投入的 5,000 行代码是资产还是沉没成本。

第 8 节补充了一类此前不在任何规划里的缺口，其中最重要的一条是：**这个项目目前对编辑器的感知为零**——不知道用户在看哪个文件、选中了什么，也看不到编译错误。把它整体搬到终端里运行几乎不损失能力，而这动摇了做成 VS Code 扩展的理由。相比之下它的修补成本很低，API 都是现成的，因此建议把 IDE 集成（方案 J）与文件生命周期工具（方案 K）插到第 7 节全部内容之前。同一节还有一个投入产出比很高的方向调整：接入 LSP 之后，路线图里"代码语义索引"这个大工程大概率可以取消。

至于第 7 节讨论的 Plan 模式、Skills、跨会话记忆和多 Agent，全部压在阶段 15 之上，现在都动不了。**在它们之间做选择之前，先建评测基线** —— 否则每一次策略调整都只能靠感觉判断好坏，而这恰恰是这类改动最不能靠感觉的地方。

最后是第 9 节的判断：把上述规划全部做完，项目达到的是 **Preview 质量而非 GA**。剩下的差距主要不在功能，而在运维成熟度——跨平台证据、会话删除、数据迁移、成本护栏、诊断导出、发布流水线这六项。总量不大（约两到三周），但无法靠写更多功能绕过。其中 **CI 的跨平台矩阵建议现在就加**：成本最低、发现问题概率最高，且拖得越久需要回头返工的平台相关代码越多。
